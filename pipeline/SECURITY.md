# Pipeline ingress security

## Upload ingress

Tasker must use the stable Cloudflare Worker endpoint:

```text
POST https://recordings.alf-broadcast.co.uk/upload-url
```

and continue sending the existing `x-recordings-auth` shared secret. The Worker rejects missing/invalid client authentication before AWS is invoked, then signs the origin request with AWS SigV4 using the dedicated `recordings-worker-invoker` IAM principal.

The deployed `recordings-upload` Lambda Function URL uses `AWS_IAM`. The invoker identity policy grants only `lambda:InvokeFunctionUrl` and `lambda:InvokeFunction` for `recordings-upload`, with `lambda:InvokeFunction` constrained to Function URL invocation. Because the Worker principal and Lambda are in the same AWS account, no Lambda resource-based allow policy is required. The previous public `Principal: '*'` upload permissions are removed from the deployed CloudFormation stack.

The Lambda still validates `x-recordings-auth` as defence in depth. A successful request returns a 900-second presigned S3 `PutObject` URL scoped to a generated `inbox/...` key. Tasker uploads the audio directly to S3; recording bytes do not traverse Cloudflare or Lambda.

## Callback ingress

Downstream automation receives a callback URL under the same stable Cloudflare domain:

```text
POST https://recordings.alf-broadcast.co.uk/recordings/callback/<64-hex-capability>
```

The callback ID is generated from 32 cryptographically random bytes (256 bits) and is the bearer capability. It is stored with the Step Functions task token only in the private DynamoDB callback table and expires after one hour. The raw task token is never exposed in the callback URL or downstream payload.

Cloudflare validates the callback route shape, JSON body, and `status` (`success` or `failed`) before invoking AWS. It then SigV4-signs the request using the same least-privilege `recordings-worker-invoker` IAM principal. The deployed `recordings-callback` Function URL uses `AWS_IAM`; its former anonymous `Principal: '*'` permissions are removed. Therefore possession of the raw Lambda Function URL is insufficient to invoke the callback Lambda.

The Lambda remains the authoritative capability validator. It rejects unknown and expired callback IDs, optionally verifies `recordingId`, atomically claims a pending callback, and uses conditional DynamoDB updates so only the first terminal callback can release Step Functions. Replays after completion are acknowledged as duplicates without invoking Step Functions again. The task token is removed after terminal completion.

Malformed callback paths and invalid JSON/status values are rejected at Cloudflare before consuming Lambda invocations. Valid-looking but unknown random capability IDs still require a Lambda/DynamoDB lookup; their 256-bit entropy prevents practical guessing of a live capability.

## Deployment hardening

`pipeline/deploy.sh` applies the Function URL hardening transform to `.aws-sam/build/template.yaml` before every supported deployment, including deployments that reuse CI-built SAM artifacts. The transform fails closed unless both upload and callback Function URLs and their expected public permission resources are present. It changes both origins to `AWS_IAM`, removes the public Lambda permissions, and sets `CALLBACK_BASE_URL` to the Cloudflare public domain.

The ingress deployment resolves both Lambda Function URLs from AWS and supplies them to the Worker as non-secret runtime configuration. The Worker's AWS access key remains stored only as Cloudflare secrets and its IAM policy permits Function URL invocation only for `recordings-upload` and `recordings-callback`.

## Verification after deployment

1. `GET https://recordings.alf-broadcast.co.uk/healthz` should return the Worker health response.
2. `POST https://recordings.alf-broadcast.co.uk/upload-url` without `x-recordings-auth` should return `401` without invoking Lambda.
3. Both underlying Lambda Function URLs should reject unsigned direct requests after the `AWS_IAM` cutover.
4. A valid upload request should still return a presigned S3 upload URL.
5. A malformed callback path, invalid JSON body, or unsupported callback status should be rejected at Cloudflare.
6. A valid callback URL generated by the pipeline should complete/fail the waiting Step Functions task once; a replay should be returned as a duplicate without releasing it again.
7. An expired callback should return `410`, and an unknown well-formed capability should return `404`.

## Rollback

If Worker-to-Lambda SigV4 invocation fails after cutover, revert the hardening change and redeploy the pipeline and ingress together. Do not expose Step Functions task tokens or proxy recording audio through the Worker/Lambda as a workaround.
